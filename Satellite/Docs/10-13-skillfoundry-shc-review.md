# Departures from your instruction

1. The fitter's folder carries a sixth bundled file, the small library shim that the existing design skill ships beside its five modules. The handoff names five modules. Those five import the shim, and the copy is byte-identical to the shipped one.
2. The fitter takes the data file as an argument, as items 4 and 5 of the SkillFoundry checklist ask, and refuses a file whose name is not data.csv. The bundled modules read data.csv from the working folder when they are loaded, so the fitter changes into the folder of the given file before loading them. This is one way to settle the first known conflict between the checklist and the harness.
3. The test commands in the metadata run from the skill folder, where the model works, and not from a repository root as in SkillFoundry. This settles the second known conflict.
4. The Environment Setup sections give the versions and a pre-flight check but no install command, no environment recipe and no offline fallback, which item 2 asks for. The sandbox has no network and the packages are present, so an install command would fail.
5. The steps that write the specification, the program and the answer show the file's shape with placeholders in angle brackets, which item 1 forbids. Concrete values there would act as a default design, and both skills leave the design to the model. For the same reason the written-code skill shows library usage only for reading the data and not for fitting weights.
6. The section headings are the nine names of the checklist, split into When to use and When not to use as in the most complete SkillFoundry skills, and the three headings of the existing settings reference. They are not complete sentences. The checklist names its sections and the ported validator checks those names.
7. The written-code skill carries the new data viewer. The handoff names new scripts for the provided-code skill only. The validator requires a scripts folder in every skill, the existing implement skill offers a data viewer, and item 5 applies to every helper script.
8. The written-code skill has no fitter, so the plan's four kinds of test are read this way for it. Execution and guard test the data viewer. The planted weights are recovered by exact least squares inside the test. Parity runs the source notebook's code in the place of the model's program. It is the same program the existing dry-run check SK5 runs, and it is kept with the test fixtures where the model cannot see it.
9. Both skill files keep the header with a name and a description that the task text is built from. The SkillFoundry skill named as the model to imitate has no such header, and 39 of the 267 SkillFoundry skills have one.
10. The section layout follows the checklist and not the model skill, whose file has four sections (What it does, When to use it, Example, Verification). The handoff makes the checklist binding where the two disagree. None of the 267 SkillFoundry skills carries all nine sections under the checklist's names, and 29 carry them when a section on failure modes stands for troubleshooting.
11. The six bundled modules of the provided-code skill are listed by sha256 and not reprinted, although the model can read them. They are byte-identical to the modules the design skill mounts today, and one of them is the source notebook's extracted code of 1,802 lines.
